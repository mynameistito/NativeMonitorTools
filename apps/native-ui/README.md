# Native Monitor Tools UI

The Native SDK shell for Native Monitor Tools is authored in TypeScript and declarative Native markup. `src/core.ts` owns the model and message loop; `src/app.native` owns the native-rendered view. The shell intentionally does not import the Bun desktop runtime, Effect, or the shared backend package.

The core sends versioned requests through the generated `backend.request` service. That service launches the Bun/Effect desktop backend using its bounded Native UI frame protocol; until the backend is available, the UI stays honest with loading, empty, unsupported, and error states rather than fabricating monitor data.

The service and backend use bounded binary frames:

- display list: `[version:u8, kind:1, count:u16]`, then each display's length-prefixed UTF-8 stable monitor `id`, `primary:u8`, `name`, `resolution`, and `position`, followed by `colorSupported:u8` and `windowToolsSupported:u8`;
- color list: `[version:u8, kind:4, count:u16]`, then each monitor's `id`, display name, gamma support/reason, and brightness/contrast support records. Supported physical levels carry `minimum:u16`, `current:u16`, and `maximum:u16`; unsupported records carry a reason and are rendered disabled;
- profile list: `[version:u8, kind:2, count:u16]`, then each profile's length-prefixed UTF-8 stable profile id and `name`, followed by `summary` and `monitorCount:u16`;
- window-area list: `[version:u8, kind:6, count:u16]`, then each built-in area carries length-prefixed UTF-8 `monitorId`, `monitorName`, `areaId`, and display `name`;
- requests use `[version:u8, operation:u8, nameLength:u16, name:utf8]`; operation 1 lists displays, 2 lists profiles, and 3 previews a named profile. Operation 4 lists colors; operation 5 sets one validated control (`gamma` in hundredths, or physical brightness/contrast as `u16`) for a stable monitor id;
- operation 6 lists built-in window areas. Operation 7 snaps the foreground window and uses a length-prefixed monitor id followed by a length-prefixed area id. A successful snap returns `[version:u8, kind:7, status:0]`;
- error frames use kind `255`, followed by the operation and a length-prefixed UTF-8 diagnostic.

The decoder is deliberately isolated in `src/core.ts`. The service launches `native-monitor-tools-backend.exe --native-ui <hex-frame>`; the backend returns a hex-encoded frame so binary bytes are not passed through a UTF-8 process stream, and the service decodes it back to the generated bytes result. The backend executable is built with `bun run backend:build` and must be discoverable through `PATH`.

Windows monitor names are enriched from valid registry EDID metadata when available, while the PNP device path remains the stable identity used by the display and color operations.

## Commands

Run these from the repository root:

```sh
bun run ui:dev
bun run ui:check
bun run ui:test
```

The repository wrappers use the pinned `@native-sdk/cli@0.10.1` and materialize `node_modules/@native-sdk/core` for editor support and validation. On Windows they prepend the tracked `scripts/native-sdk-windows/include` directory to `C_INCLUDE_PATH`; its minimal `sys/types.h` supplies the Windows `ssize_t` typedef missing from `scr_runtime.h`. The root pins `@scriptc/runtime@0.0.36`, but the CLI's `scriptc`/`@scriptc/compiler` dependency remains pinned at `0.0.35`; the installed runtime-source override was tested and did not compile with that bundled compiler. An explicit `SCRIPTC_TEST_RUNTIME_SRC_DIR` is preserved. The compatibility shim does not patch `%TEMP%` or change global `SCRIPTC_CC`/`zigcc` settings. On Windows, `ui:check` is clean, but the pinned SDK's native `ui:test` and build graph currently stop at `coff does not support linking multiple objects into one` when it combines the TypeScript core archive with markup objects. That is an upstream Native SDK/Zig limitation; generated caches and global compiler settings are intentionally left untouched. The CLI is not part of the shipped binary.
